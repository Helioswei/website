核心方法论：第一性原理，从"为什么"出发

「你手上这台手机能看视频、能打游戏，但论"沉浸地读完一本书"，它未必比得上一块电纸屏。这章我们不急着写代码，先把"电子书阅读器"这个盒子拆开：为什么是电子墨水屏？为什么是 ESP32？为什么 EPUB 是个 zip 压缩包？把每个"为什么"问透，这个项目的地图就自己画出来了。」

1.1 嵌入式基础：RAM 与 Flash 为什么宝贵

先补一张最小地图：嵌入式系统是什么？一句话说，它就是专门做某一件事的微型电脑——没有显示器、键盘、风扇，只有几个芯片藏在电路板里，默默控制着家电、穿戴设备，以及电子墨水屏（EPD，靠反射环境光成像、断电后画面也不消失的省电屏幕）阅读器这类"单一用途"的设备。它和手机、电脑的区别不在"会不会算"，而在"只为一件事优化"：洗衣机是嵌入式系统，智能手表是嵌入式系统，本项目要做的电子书阅读器，同样是嵌入式系统。

本项目的大脑是 ESP32——乐鑫科技出品的低成本、自带 WiFi 与蓝牙的 MCU（微控制器，中文俗称"单片机"，可理解为把 CPU、内存、存储整合进一颗芯片的"完整小电脑"）。我们写的 C++ 代码，最终会编译成固件（firmware）——也就是"固化进硬件的程序"——烧进芯片的 Flash 存储区，掉电也不丢。真正让嵌入式与众不同、也让初学者最先卡住的，是它只有两种"记忆"，而且都少得可怜：RAM（内存，运行时放变量和暂存数据的区域，断电即失）以 KB 计，Flash（存储区，装程序和静态数据，掉电保留）以 MB 计——而你手机、电脑上的内存和硬盘，动辄就是 GB 级，差了上千倍。所以"资源受限"是嵌入式设计的默认前提：每个字节都要精打细算。这句话，后面每一章都会反复出现。

RAM 不够用怎么办？ESP32 的部分型号支持 PSRAM——外挂在主芯片旁边、可选的扩展内存，能把可用 RAM 从几百 KB 抬到几 MB。为什么本项目把它列为第一条硬性要求？因为 EPUB（电子书打包格式，本质是个 zip 压缩包）在解压、解析 XML 时，会把整本书的内容一次性读进内存：一本带插图的古登堡书轻轻松松吃掉几 MB，而 ESP32 芯片内部只有约 520 kB 的 SRAM，没有 PSRAM 根本装不下。至于书存在哪？一般放在一张 SD 卡（可插拔的微型存储卡，本质也是 Flash）上——具体取舍到 1.3 再展开。

把"资源宝贵"记在心里，你就能看懂后面所有取舍了：解析器敢自称"Rubbish"（垃圾）HTML 解析器，是因为它不做 CSS、只认标准标签，把样式省了个干净；字体只生成黑白两色、还要压缩，是为了省内存、让翻页更快；页面得先在内存里排版完毕、再一次性刷上墨水屏，是为了少刷几次、省点功耗。每一条看似"偷懒"的设计，背后都是同一条铁律：内存和存储就那么点，得省着用。

存储作用断电是否保留量级在本项目里的用途
RAM运行时暂存区：变量、解析结果、页面缓冲断电即失KB 级（ESP32 内部约 520 kB）放解析出的文本块与帧缓冲
Flash存储区：固件程序与静态数据掉电保留MB 级装固件本体与字体
PSRAM外挂的扩展 RAM断电即失MB 级（通常 4–8 MB）装下一整本 EPUB 解压后的内容

用一张书桌来记：RAM 是"桌面"——摆着正在干活的东西，断电（人离开）就清空；Flash 是"书架"——东西放上去能长久保存，断电也不丢；PSRAM 等于又加了一张折叠桌。后面每次听到"内存紧张"，先想想：是桌面不够大（RAM），还是书架放不下（Flash / 存储）？

1.2 为什么需要自制电子书阅读器

从第一性原理出发：阅读这个场景，本质是"长时间、近距离、看静态文字"。电子墨水屏（E-ink）几乎是为这个场景量身定做的。它有两个杀手级特性：一是反射式显示，屏幕本身不发光，靠反射环境光成像，和纸张一样柔和；二是双稳态（bistable），像素在断电后依然保持显示状态——也就是说，画面定格后屏幕不再消耗任何电能，只有翻页那一下才需要供电。加上没有背光、没有频闪，长时间看书也不容易疲劳。

对比手机或平板，差距就更明显了。无论是 LCD 还是 OLED，屏幕都主动发光，还要靠 PWM 调光控制亮度，长时间盯着屏幕眼睛容易酸胀；而且只要画面亮着，电池就在持续放电——哪怕你只是停在一页上发呆。而电子墨水屏"渲染一帧、定格显示、需要时再刷新"的工作方式，让一本书可以在一节电池上读几周。这个差异，正是自制阅读器存在的第一性理由。

当然，选择从来都是取舍。电子墨水屏的代价同样明确：刷新很慢（全屏刷新需要数百毫秒）、常见的单色方案只有黑白两色、完全无法播放视频或流畅滚动。它的编程模型因此和普通屏幕完全不同——不是"每一帧重绘画面"，而是"把整页画进缓冲 → 一次性刷到屏上 → 定格"。理解了这一点，你就理解了为什么这个项目里到处都是"先把整页内容算好、最后才 flush 一次"的代码结构。

维度电子墨水屏手机 / 平板（LCD/OLED）
发光方式反射式，借环境光背光主动发光
功耗静态零功耗，仅翻页耗电常亮持续耗电
刷新率低，全刷数百毫秒级高，60–120 Hz
护眼无背光、无频闪，接近纸张长时间阅读易疲劳
适合场景静态文字阅读视频、游戏、高频交互

1.3 项目是什么

这个项目叫 diy-esp32-epub-reader（作者 atomic14），是一个跑在 ESP32 上的 DIY EPUB 阅读器。它能解析从 Project Gutenberg（古登堡计划）等免费资源下载的 EPUB 文件，在电子墨水屏上分页渲染，并用三个按键完成所有翻阅操作。作者在 README 里直白地解释了动机："It seemed like a nice challenge - ePub files are not the most friendly format to process on an embedded device."——把最不适合嵌入式设备的格式之一，塞进一个资源极其有限的单片机里，本身就是一件很好玩的事。

硬件上它"挑食"，但底线说得清清楚楚。README 的 "What boards does it work on" 一节指出：M5 Paper，以及基于 EPDiy 的并行电子墨水屏（比如 LilyGo EPD47 / T5 4.7"）都能跑。而对板子的硬性要求有四条：PSRAM（解析 EPUB 需要相当多的内存）、三个按键（UP / DOWN / SELECT，支持高电平或低电平有效）、一张 SD 卡（也可以用 SPIFFS 顶替，但装不下几本书）、以及可选的电池。仓库内置的三套构建环境，正是分别面向 LilyGo T5 4.7"、EPDiy V6、M5 Paper 这三块板。

三个按键就是这套交互的全部：UP 在书目列表里上移、阅读时翻上一页；DOWN 下移、翻下一页；SELECT 打开选中的书，或在阅读模式下返回书目。换句话说，这个"操作系统"就是一本书单、一个阅读器、三个按钮——极简到只剩骨架，却足以完成"找书、打开、翻页"的完整闭环。

# README · "What boards does it work on"（需求清单）
- PSRAM - parsing the ePub files needs a fair amount of memory
- 3 Buttons - these buttons can be active high or low
  - UP - moves up in the list of ePubs or to the previous page when reading
  - DOWN - moves down in the list of ePubs or to the next page when reading

- [Optional] A battery if you want it to be portable

为什么 EPUB 离不开 PSRAM？EPUB 整本书是一个 zip 压缩包，解压和 XML 解析都会把内容一次性读进堆内存；一本带插图的古登堡书很容易达到数 MB。而 ESP32 内部 SRAM 只有约 520 kB，没有外挂 PSRAM（通常 4–8 MB）根本装不下。所以 README 把 PSRAM 列为第一条硬性要求——这不是可选优化，是能跑与不能跑的分界线。

1.4 解剖仓库

打开仓库根目录，先别被文件数量吓到——真正的"应用"集中在两处：src/ 是固件本体，lib/ 是自带依赖。src/main.cpp 是程序入口，它定义了一个三态状态机（SELECTING_EPUB → SELECTING_TABLE_CONTENTS → READING_EPUB），用一个 FreeRTOS 消息队列接收按键事件，把"书目列表 → 目录 → 阅读"串成一个循环。同目录的 boards/ 是板级抽象层：Board.h 定义接口与 factory() 工厂方法，编译期根据宏实例化 Lilygo_t5_47、Epdiy、M5Paper 三块板中的一块。

lib/ 是重头戏。作者自己写的核心在 Epub/，内部又分四个子模块：EpubList（书目、阅读器、目录）、ZipFile（zip 解压封装）、RubbishHtmlParser（HTML 解析、换行与分页）、Renderer（渲染抽象：EpdiyRenderer、M5PaperRenderer、ConsoleRenderer 等）。其余全是第三方库：epdiy（电子墨水屏驱动）、miniz-2.2.0（zip）、tjpgd3（JPEG 解码）、png/PNGdec（PNG 解码）、sd_card、spiffs、Fonts、Images、touch（FT6X36 触摸）。

剩下的文件是"配置与资产"。platformio.ini 定义 4 套构建环境；sdkconfig.epdiy、sdkconfig.lilygo_t5_47、sdkconfig.m5_paper 是随仓库提交的三份 ESP-IDF 配置；partitions.csv 划分 Flash 分区；data/ 放着两本示例书（pg43-images.epub、pg14838-images.epub，都来自古登堡）；scripts/ 是字体与图片生成脚本（generate_fonts.sh）；test/ 搭配 fixtures/ 是能在本机跑的单元测试。

1.5 工作流程一瞥

把整条流水线串起来看，就是全书的主线：EPUB 文件本质上是一个 zip 压缩包，里面装着若干 XML/XHTML 文件。第一步用 miniz 解包；在压缩包里找到 OEBPS/content.opf（一份 XML），用 TinyXML2 解析出三样东西——metadata（书名、作者、封面）、manifest（所有文件清单）、spine（阅读顺序）。随后按 spine 顺序读取每一章的 XHTML。

每个章节 XHTML 由 RubbishHtmlParser 解析成一串 blocks（文本块或图片块）；文本块在 TextBlock::layout 里先测量每个单词的宽度，再用动态规划把单词切成行（支持两端对齐 JUSTIFIED 与居中 CENTER_ALIGN）；接着 RubbishHtmlParser::layout 把行和图片分配到页面上——页高放不下就新建一页。渲染时逐词画进帧缓冲，最后一次性 flush_display() 刷上屏幕。整个过程对用户来说，就是"按一下键、翻过一页"。

用户空闲后，系统进入深睡眠：main.cpp 里 120 * 1000 * 1000 微秒（也就是 120 秒）没有交互，就调用 renderer->dehydrate() 把渲染状态存进文件系统、停掉文件系统、配置唤醒方式（低电平按键用 ULP、高电平按键用 EXT1），最后 esp_deep_sleep_start()。醒来后从 RTC 内存恢复"在读哪本书、第几页"，继续阅读。

1.6 关键技术栈

把 1.5 流水线里的每一环"是谁实现的"列出来，就是完整技术栈。构建层是 PlatformIO + ESP-IDF（platform = espressif32、framework = espidf）；屏幕驱动是 EPDiy；zip 解包用 miniz（一个针对 ESP32 改造、支持 PSRAM 与多文件归档的版本）；XML/XHTML 解析用 TinyXML2；图像解码是 tjpgd3（JPEG）+ PNGdec（PNG）；字体由 scripts/generate_fonts.sh 基于 freetype-py 生成，只输出两色、经过压缩，让翻页更快。

整套栈里最值得单独讲的是动态规划换行——全书第 10 章的主角。TextBlock::layout 把"怎么把单词排成行"建模成最小代价问题：dp[i] 表示从单词 i 开始那一行的最小代价，代价定义为每行右侧空白的平方（最后一行除外）。它从最后一个单词向前递推，把最优的行尾下标记进 ans[]。README 还贴心地引用了 MIT 公开课（"Dynamic Programming II: Text Justification, Blackjack"）作为入门参考。

为什么选这套栈？本质是约束匹配：EPUB 需要 zip + XML 处理，就选体积小巧的 miniz 与 TinyXML2；屏幕是 EPDiy 并行墨水屏，就直接复用 EPDiy 驱动；需要在极窄内存里排版，就自己手写动态规划而非引入重量级排版引擎。每一环都是对"嵌入式资源约束"的一次取舍——理解了这个取舍逻辑，你就能从无数开源库里挑出对的那几个。

/* TextBlock.cpp：动态规划换行的核心（节选） */
int n = word_widths.size();  // 单词个数
int dp[n];                   // dp[i] = 从单词 i 开始那一行的最小代价
size_t ans[n];               // ans[i] = 该行最后一个单词的下标

dp[n - 1] = 0; ans[n - 1] = n - 1;
for (int i = n - 2; i >= 0; i--) {
  int currlen = -1; dp[i] = INT_MAX;
  for (int j = i; j < n; j++) {
    currlen += word_widths[j] + space_width;   // 当前行宽（含单词间空格）
    if (currlen > page_width) break;
    int cost = (j == n - 1) ? 0
              : (page_width - currlen) * (page_width - currlen) + dp[j + 1];
    if (cost < dp[i]) { dp[i] = cost; ans[i] = j; }  // 记下最优方案
  }
}

章末练习

练习 1：电子墨水屏 vs 屏幕 入门

结合 1.2，列出电子墨水屏适合阅读的三个理由，以及两个它明显不适合的场景。尽量用"特性→后果"的句式（例如"反射式显示 → 长时间阅读不疲劳"）。

提示

从发光方式、功耗、刷新率三个维度想；反面例子可以找"需要连续刷新"的用途。

参考答案

适合：反射式显示无背光、接近纸张，长时间阅读不易疲劳；双稳态断电后画面保持，静态零功耗，一页能停几周；仅翻页耗电，配合深睡眠可做成便携低功耗设备。不适合：播放视频与流畅滚动（刷新率太低、全刷数百毫秒）；需要彩色的高频交互界面（单色方案只有黑白）。

练习 2：仓库解剖 入门

打开 diy-esp32-epub-reader 仓库，指出以下四处的位置：(a) 固件程序入口在哪个文件？(b) 三块板的实现在哪个目录？(c) 两本示例书放在哪？(d) 4 套构建环境定义在哪个文件？

练习 3：读状态机 进阶

读 src/main.cpp 里的 UIState 状态机，回答：三个状态之间由哪个按键动作触发切换？状态为什么放在 RTC_NOINIT_ATTR / RTC_DATA_ATTR 内存里？

提示

SELECT 是"前进"：书目 → 目录 → 阅读；阅读中 SELECT 返回书目。RTC 内存在深睡眠期间不掉电。

参考答案

SELECTING_EPUB（书目）按下 SELECT → SELECTING_TABLE_CONTENTS（目录）；再按 SELECT → READING_EPUB（阅读）；阅读中按 SELECT 回到 SELECTING_EPUB。状态放在 RTC 内存里，是因为系统会进入深睡眠——RTC 域在睡眠时保持供电，醒来后仍能读到"在读哪本书、第几页"，实现无缝续读。

练习 4：第一性原理推演 挑战

用第一性原理解释两件事：(1) 为什么 README 把 PSRAM 列为硬性要求？(2) 换行问题为什么用动态规划而不是更简单的贪心（每行塞到放不下为止）？请给出你的推理链。

提示

从"EPUB 是 zip + XML"推出解析时的峰值内存需求；贪心是"局部最优"，DP 追求"全局最优"——想想两种做法各自的代价函数长什么样。

参考答案

(1) EPUB 整本是一个 zip，解包与 XML 解析都要把内容读进堆内存，带插图的古登堡书可达数 MB；ESP32 内部 SRAM 仅约 520 kB，没有外挂 PSRAM 根本无法容纳——所以这是"能跑与不能跑"的分界。(2) 贪心每次把行塞到放不下为止，结果是右缘参差不齐、空白分布不均匀；DP 把代价定义为"每行右侧空白的平方和"（最后一行除外），从全局寻找让代价最小的断行方案，排版更均匀美观。代价是 O(n²)，但一行里的单词数有限，实际可以接受。这正体现了"在约束下求全局最优"的工程权衡。
